## 本轮结论

项目具备候选录入、筛选、达人详情、AI/本地首封邮件草稿及 Gmail 草稿能力，但流程以「邮件草稿管理」为中心。针对这次 60 张 TikTok Shop 候选卡片，当前主要耗时在逐个录入、核实已邀历史、判断内容适配和整理具体切入点。先解决数据入口与联系前核验，再改写文案或接入自动化，收益最大。

在截图样本中，29/60 人符合原定 100–1,000 粉条件；这只是粉丝数初筛。建议先核验其中 6 人，确认主页、近期作品、受众市场、既往邀约和竞品关系后再定正式邀约名单。

## 主要问题与优先级

| 优先级 | 问题 | 代码位置 | 影响 |
|---|---|---|---|
| P0 | 单人「标记已发送」可直接写入 `sent`，不记录渠道、时间、操作者或外部凭据 | `app.py` 中 `/creators/<id>/action` 的 `sent` 分支 | 虚假的发送状态会触发错误的跟进判断；TikTok/私信人工发送也需要可核查记录 |
| P0 | 候选去重只检查同项目 `profile_url`；URL 为空时不查用户名与平台 | `app.py` 中 `/screening/candidates` | 截图候选重复录入，可能重复准备或联系 |
| P0 | 不保存 TikTok 后台「以前邀请过」的时间、渠道、结果和拒绝联系状态 | `creators` 表与筛选表单 | 无法在邀约前排除已联系、已拒绝或正在沟通的人 |
| P1 | 每次只能录入 1 位候选；没有批量预览、字段映射和错误回退 | `/screening` 表单 | 30–60 人的截图批次录入耗时，易发生转录错误 |
| P1 | 默认 `competitor_conflict=0` 同时代表「未查」和「已查无冲突」；已核验只要求国家、粉丝、链接和日期 | `creators` 表、`screening_page`、录入/编辑校验 | 筛选结果看起来比实际证据更确定 |
| P1 | 匹配分主要由平台、邮箱、主页、词汇重叠、是否已有草稿构成 | `calculate_creator_score` | 生成草稿会提高商业潜力分；不能用该分数代表内容/受众适配性 |
| P1 | 任何未核验达人都能生成同一类首封草稿；缺近期作品证据也能推进批量流程 | `generate_outreach_for_creator`、`execute_campaign_action` | 容易出现泛化邮件，人工审核成本高 |

## 建议的目标流程

`批量录入 → 身份去重 → 粉丝门槛初筛 → 内容/市场/历史邀约核验 → 证据覆盖率与优先级 → 单人渠道草稿 → 人工审核 → 记录实际发送 → 跟进与回复`

状态应分别表达 **研究进度** 与 **沟通进度**。例如「待核验」可以生成内部参考草稿，但不能进入「可联系」队列；「已发送」必须有人工填写的渠道、时间和可追溯备注。不要要求所有平台都先创建 Gmail 草稿。

## 分期实施

### P0：先让名单与发送状态可信（预计 1–2 个开发日）

1. 定义唯一账号键：`platform + normalized_handle`；有主页 URL 时再用规范化 URL 做二次匹配。批量或单条录入遇到重复时返回现有档案，不静默新建。
2. 增加历史联系字段：`contact_history_status`（未知/后台显示曾邀/已联系/已回复/拒绝继续联系）、最近联系时间、渠道、来源与备注。拒绝继续联系作为明确阻断条件；「截图未见曾邀」保留为未知。
3. 修改「标记已发送」：要求渠道、发送时间和人工确认；记录为独立沟通事件。Gmail 草稿 ID 只能证明创建草稿，不能证明邮件已发。保留对 TikTok/Instagram 人工发送的记录入口。
4. 给批量生成和批量创建 Gmail 草稿加可见的前置检查与跳过原因：身份未核实、历史邀约未查、已拒绝、竞品状态未知、缺渠道或文案审核等。允许单人保存探索草稿，但明确标为「不可直接发送」。

**验收**：同账号重复提交只保留一条；无发送凭据不能进入 `sent`；拒绝联系者不会进入可联系队列；每个被跳过的账号能看到具体原因。

### P1：把截图候选快速变成可审名单（预计 2–3 个开发日）

1. 增加粘贴表格/CSV 导入与预览。用户不能从 TikTok 导出 CSV 时，可把人工转录的表格粘贴进来；系统逐行检查账号、粉丝数、来源截图编号、观察日期，先预览再确认入库。图片识别可后置，初版不依赖抓取 TikTok。
2. 把 `competitor_conflict` 拆成「未知/已查无冲突/有冲突」，并补充核验卡：主页 URL、近期相关视频 URL、内容语言、受众国家及其来源、观察日期、历史邀约结果、可用商务渠道。
3. 筛选页提供「仅粉丝门槛符合」「待补证据」「可联系」「已排除」四个视图；每人显示缺什么，而不只显示一个笼统的已核验标记。

**验收**：30 条候选可一次粘贴预览，重复和缺字段逐条提示；29 条符合粉丝范围的截图候选可录为「待核验」，不会误标为「已核验」。

### P2：提高定制质量与可比较性（预计 2–3 个开发日）

1. 将现有运营进度分与「达人适配分」分开。适配维度建议：相关内容 30、目标市场受众 25、内容交付质量 20、合作可执行性 15、预算匹配 10。未知维度不按 0 分处理，同时显示证据覆盖率；覆盖率不足 70% 只列「待补证据」。
2. 给每封首邀保存一个已核验的**具体内容切入点及链接**、合作目的、渠道（邮件/私信）和语言。无切入点时生成诚实的通用探索稿，不伪称看过作品。邮件与私信分别生成适合的长度。
3. 草稿审核页检查占位符、未经确认的报价/佣金/寄样/配送承诺、品牌与市场表述、阿英版本关键条件一致性。保存「草稿版本 → 审核人 → 最终发送文本」关系。

**验收**：同一批 6 位优先核验者的草稿各有不同且可追溯的内容切入点；缺证据时不虚构；旧的 `match_score` 不再充当内容适配排名。

### P3：小规模验证与迭代（约 1 周运营观察）

先拿这轮 29 位符合粉丝门槛的候选试运行；人工核验 6 人，不急于全量录入或自动邀约。记录每人核验用时、重复率、资料完整率、被跳过原因、个性化草稿审核通过率。若实际开展触达，再记录按渠道的回复率和有效沟通率；不要用截图里的 GMV、成交件数直接推断本项目 ROI，因为统计口径和期间未显示。

## 推荐的开发顺序

先做 P0 的状态与去重，再做 P1 的批量录入，然后做 P2 的评分与草稿。每期只扩大一个环节的自动化范围，并以真实的截图批次做回归样本。当前项目不需要自动抓取 TikTok，也不需要自动群发；两者不会解决名单真实性和文案针对性问题。
